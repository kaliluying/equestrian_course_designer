# 第一阶段优化设计：后端安全修复 + 前端配套改动

日期：2026-07-05

## 背景

当前项目在协作分享、WebSocket 准入、支付落账一致性方面存在几类高优先级问题：

1. `Design.is_shared` 同时承担“公开分享”和“允许加入实时协作”的语义，权限边界过宽。
2. 分享链接 token 内直接携带 `password_hash`，虽然经过签名，但不利于撤销、审计与后续安全演进。
3. 支付回调与轮询查询分别落账，存在并发条件下重复加配额或重复续费的风险。
4. 认证与协作相关日志输出过多上下文，不适合生产环境。
5. 前端协作接入依赖旧的分享链接判断逻辑，需要做最小范围适配。

本阶段目标是在不重做整体产品流程的前提下，把最危险的问题收口，并为后续更彻底的协作重构打基础。

## 目标

本阶段覆盖以下内容：

1. 修复 WebSocket 协作权限模型
2. 调整分享链接密码与撤销机制
3. 统一支付幂等落账入口
4. 收敛敏感日志
5. 完成前端最小必要配套改动

不在本阶段处理：

- 大规模前端组件拆分
- `course.ts` / `websocket.ts` / `CollaborationPanel.vue` 的结构性重构
- 导出异步化
- 评论与协作事件分页
- 全量 CI / lint / 工程化补齐

## 设计概览

### 1. 协作分享授权模型

新增一个轻量持久化分享链接实体，用于表达“谁可以通过该链接加入协作会话”。

建议字段：

- `design`
- `created_by`
- `role`
- `expires_at`
- `password_hash`
- `is_revoked`
- `created_at`
- `updated_at`

该模型只负责协作准入，不承担“公开展示”语义。

`Design.is_shared` 保留，但语义收敛为：

- 当前设计是否处于公开分享/可见状态
- 不再作为实时协作准入条件

### 2. 分享 token 设计

当前 token payload 中直接放 `password_hash`。本阶段调整为只放：

- `share_link_id`
- `design_id`
- `scope`

WebSocket 建连时：

1. 验证签名
2. 读取 `share_link_id`
3. 回查分享链接记录
4. 校验：
   - link 是否存在
   - 是否已撤销
   - 是否已过期
   - `design_id` 是否匹配
   - `scope` 是否匹配
   - 如果设置了密码，使用 Django 密码校验函数验证

这样可以实现：

- token 泄露时不暴露密码 hash
- 服务端撤销即时生效
- 后续支持使用次数限制、审计日志等演进能力

### 3. WebSocket 权限模型

本阶段把协作准入统一为：

1. 设计作者
2. 已存在的显式协作者/角色记录
3. 持有有效分享链接的用户或匿名访问者

这意味着：

- `check_design_access()` 不再把 `design.is_shared` 视为可协作
- 匿名访问只允许通过有效分享链接进入
- 登录用户如果不是作者，也不是显式协作者，则仍需有效分享链接

### 4. 支付幂等落账

把订单支付成功后的状态变更与业务落账收敛到单一事务入口。

建议新增统一结算函数，内部执行：

1. `transaction.atomic()`
2. `select_for_update()` 锁定订单
3. 二次检查订单状态是否已完成落账
4. 若未完成：
   - 更新订单状态
   - 记录 `trade_no`
   - 记录 `payment_time`
   - 调用会员或 AI 配额落账逻辑
5. 若已完成：
   - 直接返回成功，不重复发放权益

`alipay_notify()` 与 `get_order_status()` 都调用该统一入口。

### 5. 日志策略

需要删除或收敛以下日志：

- cookie 名称与 token 存在性细节
- WebSocket `scope` 全量日志
- 过多的调试级连接日志

保留的日志字段应尽量最小化：

- `user_id`
- `design_id`
- `share_link_id`
- `order_id`
- 错误类型

生产环境不输出可推断认证细节的日志内容。

### 6. 前端配套改动

本阶段前端只做最小适配，不做整体协作 UI 重写。

范围包括：

1. 分享链接生成后继续使用现有入口和交互
2. 加入协作时，若需要密码，按新的后端校验语义继续传递密码
3. 根据新的错误原因展示更明确提示：
   - 链接已撤销
   - 链接已过期
   - 密码错误
   - 无权限加入
4. 不再依赖旧的“设计已共享即可加入协作”隐含逻辑

## 数据流

### 分享链接生成

前端请求 `ShareLinkView` → 后端创建分享链接记录 → 生成只包含引用信息的 token → 返回分享 URL、token、到期信息、是否启用密码。

### 分享链接加入协作

前端通过 WebSocket 发起连接，并携带 token（如有需要则附带密码） → consumer 验证 token → 回查分享链接记录 → 校验通过后加入协作会话。

### 支付成功

支付宝回调或前端轮询查询命中支付成功 → 统一结算函数加锁并落账 → 若订单已处理则直接返回成功语义。

## 错误处理

### 分享链接相关

细分错误原因：

- 链接不存在
- 链接已撤销
- 链接已过期
- 密码错误
- 设计不匹配
- scope 不匹配

### 支付相关

- 并发回调/轮询造成重复提交时，不重复发放权益
- 支付配置缺失仍返回明确可观测错误
- 异常情况下优先保证订单和权益状态一致

## 测试策略

### 后端

新增或补强测试：

1. 作者可生成与撤销分享链接
2. 已撤销链接不可加入协作
3. 已过期链接不可加入协作
4. 密码错误不可加入协作
5. `design.is_shared = true` 但没有协作授权时，不可直接加入协作
6. 匿名用户仅能通过有效分享链接进入
7. 支付回调与轮询并发触发时，只落账一次
8. AI 配额订单不会重复增加配额
9. 会员续费不会因重复回调重复延长

### 前端

新增或补强测试：

1. 协作加入失败原因映射正确
2. 密码加入流程可正常提交与提示错误
3. 旧的共享判断不再误导协作入口行为

## 迁移策略

1. 先新增分享链接模型与迁移
2. 后端兼容现有分享链接生成接口返回结构
3. 前端在不改变主要页面结构的前提下适配新的错误原因
4. 切换 WebSocket 权限逻辑
5. 最后收敛日志与支付幂等入口

## 风险与控制

### 风险

1. 协作链接老数据兼容
2. WebSocket 鉴权改动可能影响现有协作接入流程
3. 支付幂等调整可能影响现有订单状态判断

### 控制措施

1. 保持现有分享接口返回字段尽量稳定
2. 先补测试，再切换权限判断
3. 支付逻辑统一后，以订单状态与权益结果双重断言验证

## 交付结果

本阶段完成后应达到：

1. `design.is_shared` 不再直接授予协作权限
2. 分享链接密码不再以内嵌 hash 方式存在于 token 中
3. 支付回调与轮询共用单一幂等落账入口
4. 敏感认证/连接日志明显减少
5. 前端协作接入在现有体验下保持可用
